# Spike 1：ABP 规则引擎 benchmark（风险 R4）

- 日期：2026-07-19
- 环境：.NET 8.0.29，X64，Windows，Release 构建
- 代码：`spikes/AdBlockSpike/`（独立 .NET 8 控制台项目，未加入 Apage.sln）
- 复现：`dotnet run -c Release --project spikes/AdBlockSpike`（固定 seed 42/43/44，结果可复现）

## 方案（docs/product-design.md §5.3）

每条网络规则提取一个 **3-8 字符的字母数字关键子串**作为 key，建 `Dictionary<string, List<Rule>>` 索引；
匹配时枚举 URL 的全部 3-8 字符子串查表，只对命中的少量候选规则做正则校验，而不是对全量规则逐条正则。
所有正则统一 `MatchTimeout=100ms`，懒编译（只有成为候选才编译）。

## 测试数据

- 规则 500,000 条（固定 seed 合成）：
  - 网络拦截（`||ads.xxx.com^` 类）70% = 350,000
  - 带 `$script,domain=` 等修饰 15% = 75,000
  - 化妆隐藏（`##.ad` 类）10% = 50,000（不进网络索引，仅计入内存）
  - 例外（`@@` 类）5% = 25,000
- 测试 URL 10,000 个，50% 构造为必命中（取自被拦截域名），50% 良性。
- 正式测量前先跑一轮热身（触发 JIT 与候选规则正则懒编译），热身数据不进统计。

## 实测结果

### 索引构建

| 指标 | 实测值 |
|---|---|
| 构建耗时 | 463.7 ms |
| 托管堆增量 | 86.3 MB（索引结构 + Rule 对象，不含原始规则字符串） |
| 进程工作集增量 | 104.1 MB |
| 索引 key 数 | 335,219 |
| 提取不到 key 的退化规则 | 0 |

### 单 URL 匹配耗时（稳态，10,000 次逐次计时）

| 指标 | 实测值 |
|---|---|
| 平均 | 23.84 µs |
| P50 | 12.90 µs |
| P95 | 70.90 µs |
| P99 | 205.40 µs |
| 最大 | 6,220.50 µs（单次离群，疑为 GC/慢正则） |
| 命中率 | 5,000/10,000 = 50.0%（与构造一致，无误拦良性 URL） |
| 平均每 URL 候选正则校验 | 20.05 次 |
| 匹配期 RegexMatchTimeoutException | 0 次 |

### 基线对照：逐条正则扫描

抽样 20 URL × 5,000 规则实测平均 **1.79 ms/URL**，线性外推 50 万条约 **179 ms/URL**。
子串索引平均 0.024 ms/URL，**约 7,500 倍提速**——索引方案不是优化，是必需。

### 防 ReDoS 验证

灾难性回溯规则 `(a+)+$` 对非匹配输入（45 个 `a` + `!`，无超时时回溯量为天文数字）：

- 捕获 `RegexMatchTimeoutException`：**是**
- 实际抛出耗时：**100.5 ms**（贴合 100ms 上限）

结论：统一 `MatchTimeout=100ms` 可杜绝恶意规则卡死浏览器线程，§5.3 防护机制有效。

## 结论：50 万条规则是否无压力？

**成立。** 50 万条规则下：

- 构建 <0.5s、索引内存 ~90MB 量级（便携浏览器可接受，真实列表通常 5-15 万条，实际占用更低）；
- 单 URL 平均 24µs、P99 约 205µs，对页面加载完全无感（一次导航通常涉及几十个子资源请求，全部拦截判定加起来也 <1ms 量级）；
- 例外规则用同样索引处理，命中后例外校验成本可控；
- 灾难性回溯被 100ms 超时兜住。

## 对 Apage.Core 实现的建议

1. **索引结构照搬本 spike**：`Dictionary<string, List<Rule>>`，key 为规则内最佳 3-8 字符字母数字子串；选 key 时对 `com/net/www` 等通用 token 重罚、含数字子串加分（本 spike 的评分策略把 42.5 万网络规则摊到 33.5 万个 key 上，平均每 URL 仅 20 次候选校验）。
2. **正则必须懒编译 + 统一 100ms `MatchTimeout`**；`IsMatch` 用 try/catch 包住，超时视为不匹配并计数上报。禁止预热编译全量规则（数十万正则编译会拖垮启动）。
3. **`^` 分隔符的转换注意**：`^` 的正则会消费一个字符，`||domain^/path` 这类写法在 ABP 语义里要求分隔符后再有一个 `/`，实际匹配不到——转换逻辑与列表导入后的自校验都要覆盖这个坑（本 spike 首轮即因此漏判 24% 的应命中 URL）。
4. **化妆规则不进网络索引**：按域名分桶存储即可，不占 URL 匹配路径。
5. **退化桶**：提取不到 key 的规则（纯正则规则等）保留逐条校验桶，并限制其数量上限（§5.3 的单列表条数上限同理）。
6. **进一步优化空间**（非必需）：枚举 URL 子串时的 `Substring` 分配约占匹配成本大头，未来可用 `CollectionsMarshal`/span 查表或固定长度分桶消除分配；离群的最大 6.2ms 单次耗时如在意可排查慢正则并单独设更严超时。
